Rotierende vs. Sticky Sessions: wann welche scheitert

Sie lösen gegensätzliche Probleme, und die falsche Wahl erzeugt einen Fehler, den man kaum sieht: Der Code läuft, die Anfragen liefern 200 — und die Daten sind still und leise falsch.

Der Unterschied in einem Satz

Rotierend liefert pro Anfrage eine andere Ausgangs-IP. Sticky liefert dieselbe IP für die Dauer einer Session. Gleicher Pool, gleicher Preis, gegensätzliches Verhalten — und die richtige Wahl hängt allein davon ab, ob sich das Ziel zwischen den Anfragen an Sie erinnert.

Rotierend, wenn jede Anfrage unabhängig ist

  • Produkt- oder Listenseiten, die ohne Login sichtbar sind.
  • Öffentliche Daten, bei denen nichts zwischen Seiten mitwandert.
  • Großvolumiges Crawling, bei dem die Last verteilt werden soll.

Sticky, wenn das Ziel Sie verfolgt

  • Alles hinter einem Login: ein IP-Wechsel mitten im Ablauf wirkt wie Session-Hijacking.
  • Mehrstufige Abläufe: Warenkorb, Checkout, Buchungen, Formulare.
  • Seiten, die einmal eine Challenge stellen und danach der Adresse vertrauen.
  • Limits pro Adresse, bei denen ein IP-Wechsel Ihren Fortschritt zurücksetzt.

Der stille Fehler

Der teure Fehler ist das Rotieren innerhalb einer Session, die Kontinuität braucht. Nichts stürzt ab. Stattdessen passiert Folgendes:

  1. Die Session rotiert mitten im Ablauf, und die Seite behandelt die nächste Anfrage als neuen, nicht angemeldeten Besucher.
  2. Sie erhalten eine Login-Seite oder eine Challenge — mit HTTP 200, denn der Server hat erfolgreich geantwortet.
  3. Ihr Parser akzeptiert das und schreibt leere oder Standardwerte als echte Daten.

Sie merken es Wochen später in einem Datensatz, der vollständig aussieht und es nicht ist. Validieren Sie Antworten gegen einen bekannten Marker, nicht nur gegen den Statuscode.

Wie lange eine Sticky Session leben sollte

  • Minuten, nicht Stunden bei den meisten Aufgaben: eine Session pro logischer Arbeitseinheit.
  • Pro Konto oder Aufgabe fixieren, nicht pro Worker. Teilen zwei Worker eine feste Adresse, haben Sie genau das Parallelitätsproblem nachgebaut, das Sie vermeiden wollten.
  • Session beim ersten harten Fehler verwerfen. Auf einer bereits herausgeforderten Adresse weiterzumachen verbrennt Anfragen.

Wo Ihr eigener Stack Sie verrät

Fast jeder Bericht „Sticky funktioniert nicht“ stammt vom Client: Connection-Pooling mit fremder Session-ID, asynchroner Code mit parallelen Anfragen in einer logischen Session, eine Wiederholungsschicht, die ohne Absprache eine neue Adresse nimmt, oder Session-IDs pro Anfrage statt pro Aufgabe.

Protokollieren Sie vor jedem Schuldzuweisung die Ausgangs-IP bei jeder Anfrage eines Ablaufs und prüfen Sie, ob sie hielt. Anbieter, die die zugewiesene Adresse pro Session offenlegen, machen daraus eine Zwei-Minuten-Prüfung: IPRoyal etwa erlaubt es, eine Session-ID und ein Land gezielt anzufordern — die Adresse ist damit reproduzierbar statt geraten.

Kurzfassung

  • Rotierend für unabhängige Anfragen, Sticky für alles, woran sich die Seite erinnert.
  • Rotieren innerhalb einer Session wirft keinen Fehler — es verfälscht Daten still.
  • Eine Sticky Session pro Arbeitseinheit, verworfen beim ersten harten Fehler.
  • Prüfen Sie, ob die Ausgangs-IP über den ganzen Ablauf hielt, bevor Sie den Anbieter beschuldigen.

Letzte Prüfung: September 2026. Funktionen und Limits unterscheiden sich je nach Tarif — prüfen Sie die Anbieterseite.
